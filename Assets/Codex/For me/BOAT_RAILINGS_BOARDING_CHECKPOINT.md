# Boat railings / boarding — current-project audit (2026-10-08)

Audit performed before implementation against the current source and the railings handoff.

- `DeckBoardZone`: trigger-overlap tracking; hold-E boarding (optional secondary climb input); Down held then a fresh Jump for unboarding. `CanBoard`/`CanUnboard` drive prompts and hold progression; `TryBoard`/`TryUnboard` are authority-gated. Boarding safety tests the path to one fixed authored `boardPoint`, then tests the actual player footprint against interior visibility zones. Unboarding changes context without a positional snap. New local restriction checks must run in eligibility and again on application.
- `BoatBoardingInteractable`: separate hold-E boarding-door path through Interactor2D, with explicit board/unboard points and optional parenting. Preserve those points and visual-fade behavior; add the same local rail check.
- `PlayerBoardingState`: changes collision/sorting/mass context; boarded actors prefer ghost geometry, unboarded actors ignore hull/ghost geometry. `PhysicsFrame2D` provides existing render/physics conversions needed for moving/rotated boats.
- `GhostCollisionProxy`: discovers structure under `_Hull`/`_Deck`, copies ordinary collider geometry and synchronizes enabled state and transforms. Hull-layer rails under `_Deck` can use this without a new collision layer; ordinary cargo hits the real structure.
- Builder: `BoatKit`, `BoatBuilderWindow`, `BoatBuilderSceneTools` and its Visuals partial. Pieces are prefab-authored structural content placed with the existing grid, Transform tools and `_Deck` category; they are not hardpoint equipment modules. Installed layout persists in the saved boat prefab identity. Preserve enum IDs by appending tools.
- Existing access state: `DoorAuthoring`, `DoorRuntime`, `DoorInteractable`, `BoatAccessStatePersistence` and `BoatAccessStateManifest`. A gate can reuse this state and save format, with a unique builder-authored door ID. Door toggles use existing authority rules; networking transport is outside this mini-pass.
- Interaction: `Interactor2D` and prompt providers retain discovery/priority; suppress unavailable deck crossings before holds begin. Gate interaction must outrank deck boarding and be usable from outside. Existing independent deck hold polling needs to yield when the gate is the intended interaction.
- Art: new `RailMetal_Sprite.gif` (100×45 sprite rectangle) and `RailMetalEnd_Sprite.gif` (10×45) under Sprites/Piskel/Boat. Both use importer alignment 0 (center) and 100 PPU. The sprite-sheet pivot {0,0} was incorrectly read as the effective pivot during the initial audit; Unity imports them centered. Author physical/traversal rectangles from these extents, with adjustable prefab dimensions.

Implementation plan: explicit boat-local rail blocker footprints, preserving the broad zone; continuous local-X deck destinations on boats with rails, using the authored boardPoint as deck-height reference; fixed authored snap retained on boats without rail blockers. Candidate geometry and tests must account for rotated boats and interpolated physics. Side, end and gate prefabs are added to the existing builder. No automatic rail installation or board-zone splitting.
